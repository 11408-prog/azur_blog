# 12 安全

这一篇汇总和安全有关的约定、已知风险和已修复的问题。

## 加密文章 / 加密相册

### 它能做什么，不能做什么

- 内容在**构建时**用 AES-256-GCM 加密，读者在浏览器里输入密码后解密
- 密钥由 PBKDF2-HMAC-SHA256 从密码派生，迭代 **60 万次**
- **这不是访问控制**。密文仍随静态站点公开，任何人都能下载并离线尝试破解，所以请用**长密码**
- **仓库里是明文**：文章的 `password` 和正文都写在 `.md` 里，仓库公开就等于公开。需要保密的内容不要提交到公开仓库

### 协议（v3）

输出格式：`base64( salt[16] + iv[12] + authTag[16] + ciphertext )`，其中明文以 `MIZUKI-VERIFY:` 开头，用来在解密后确认密码正确。

实现在 `src/utils/crypto-utils.ts`，客户端解密脚本在 `src/components/features/auth/PasswordProtection.astro`。
两边的常量（迭代次数、各字段长度、验证前缀）都来自 `CRYPTO_CONSTANTS`，页面通过 `define:vars` 取用，**不要在别处手抄一份**。

### 已修复：nonce 复用

旧版本的 salt 和 IV 是用 `HMAC(密码, 文章 slug)` **确定性**派生的。文章修改后重新构建，密码和 slug 没变，就会用**同一个密钥和同一个 IV** 加密不同的明文。
在 AES-GCM 下这会泄露两段明文的异或，并让攻击者有可能伪造密文。只要两个版本的密文被缓存、存档或留在部署历史里，就会被利用。

现在每次加密都用 `crypto.randomBytes` 生成新的 salt 和 IV，所以同一篇文章每次构建的密文都不同，这是预期行为。

`tests/crypto.test.mjs` 里有"同样输入密文不同"和"20 次加密 salt+IV 都唯一"的用例，专门防止回退。

### 其他注意

- 解密成功后，密码会以明文存进浏览器的 `sessionStorage`（用于同一会话内自动解锁）。如果页面有 XSS，密码会泄露
- 新协议和旧协议不兼容，但所有加密内容都是构建时生成的，**重新构建、重新部署**即可，不需要迁移数据

## 脚本里的安全设计

- `scripts/sync-content.js`：所有 git 命令用 `execFileSync` 传参数数组，**不拼接字符串**，克隆时用 `--` 隔开仓库地址，防止被当成选项注入；`git add` 只添加内容目录，不再 `git add .`；默认不启用同步（需要 `ENABLE_CONTENT_SYNC=true`）
- `deploy-pages.ps1`：校验 token 前缀，`http.sslVerify=true`
- `scripts/sync-music.mjs`：**关闭了 TLS 证书校验**（`NODE_TLS_REJECT_UNAUTHORIZED=0`），原因和建议见 [06](./06-音乐播放器.md)
