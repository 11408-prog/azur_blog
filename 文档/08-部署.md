# 08 部署（GitHub Pages）

> 只讲怎么把站点推到线上，以及这条路上踩过的坑。站点怎么配、文章怎么写，看其他几篇。

| 项 | 值 |
| --- | --- |

## 第一次：准备 token

1. 打开 <https://github.com/settings/tokens>，创建一个 token（经典 token 勾选 `repo`，或细粒度 token 授予这个仓库的 Contents 读写）
2. 把 token **单独一行**写进项目根目录的 `.deploy-token`，文件里不要有别的内容
3. 确认 `.deploy-token` 在 `.gitignore` 里（已经在），**绝对不要提交它**

脚本只接受以 `ghp_`、`github_pat_`、`gho_`、`ghs_` 开头的 token，其他会拒绝使用。也可以用 `-Token` 参数临时传入，但那样 token 会留在命令行历史里，不推荐。
token 只在内存里使用，不回显、不写盘。

## 日常部署

```powershell
.\deploy.bat                        # 双击这个最省事
.\deploy-pages.ps1                  # 完整构建 + 推送（会要求输入 YES 确认）
.\deploy-pages.ps1 -DryRun          # 全流程跑一遍，但不推，可以看体积
.\deploy-pages.ps1 -NoBuild         # 用现成的 dist，不重新构建（最快）
.\deploy-pages.ps1 -Force           # 跳过推送前的确认
.\deploy-pages.ps1 -KeepCache       # 增量构建（刚换过图片时别用）
```

脚本做的事：

```
检查工具 → 读凭据 → 测试连通 → 停掉占端口的 dev → 清 dist 和图片缓存
→ astro build → pagefind 搜索索引 → 校验产物 → 复制到 .publish 并剔除模板垃圾
→ 补 .nojekyll → 建提交 → force push 到 gh-pages → 报出线上地址
```

> 脚本直接调用 `node node_modules/astro/bin/astro.mjs build` 和 pagefind，**不经过** `pnpm build` 的样式检查和字体检查。
> 它还会把 `ENABLE_CONTENT_SYNC` 设成 `false`。

### `auto-deploy.cmd`：部署 + 提交源码

它会依次做四件事：

1. 运行 `deploy-pages.ps1 -Force`（可以选择跳过重新构建）
2. `git add -A` 并提交源码（提交说明留空则用时间戳）
3. `git fetch` + `git rebase origin/main`，再推送到 `main`
4. 汇总两边的结果

注意：

- 第 2 步是 `git add -A`，**会提交所有未被 `.gitignore` 忽略的文件**，所以 `.gitignore` 必须保持完整，提交前最好 `git status` 看一眼
- 第 3 步用的是系统自带的 git 配置，**不带 `deploy-pages.ps1` 里的 openssl 绕过**。如果你的机器上 git 的 TLS 有问题（见下文），这一步会失败，但前面的网站部署不受影响

## 三个必须知道的坑（都已写进脚本）

> 下面三个是**作者那台 Windows 机器**上实测遇到的环境问题。别的机器上可能一个都不会发生，但脚本里的处理对它们无害。

### 1. git 连不上 GitHub：schannel 损坏

```
fatal: unable to access 'https://github.com/...': schannel: AcquireCredentialsHandle
failed: SEC_E_NO_CREDENTIALS (0x8009030e)
```

根因：`C:\Program Files\Git\etc\gitconfig` 里系统级写死了 `sslBackend = schannel`，而 Windows 的 schannel 在这台机器上拿不到凭据句柄。不是网络封锁。

解法：强制走 OpenSSL 后端，并显式指定 CA 证书。脚本每次调用 git 都带上：

```
-c http.sslBackend=openssl -c http.sslVerify=true -c http.sslCAInfo=<Git 自带的 ca-bundle.crt>
```

### 2. 凭据读不出来：credential helper 起不来

```
sh: *** fatal error - couldn't create signal pipe, Win32 error 5
fatal: unable to get password from user
```

根因：git 调 credential helper 要经 `sh.exe`，而它在某些受限环境（沙箱 / 安全代理）里建不出管道。

注意 `git ls-remote` 是**匿名请求**，所以它能通；一旦 `push` 需要认证就卡死。**别用 `ls-remote` 成功来证明"git 好了"。**

解法：不依赖 helper，由脚本直接把 token 通过 `http.extraheader` 以 Basic 认证塞给 git，并设 `credential.helper=` 为空。

> 旧版本的脚本是从 Git Credential Manager 里读 token，现在改成读 `.deploy-token`。`deploy-pages.ps1` 文件头的说明如果还写着 GCM，以这里为准。

### 3. 缺 `.nojekyll` = 整站白屏

GitHub Pages 的 legacy 构建走 **Jekyll**，Jekyll 默认忽略所有 `_` 开头的目录。而 Astro 的全部产物都在 `_astro/` 里，没有 `.nojekyll` 就是 **CSS 和 JS 全 404、整站白屏**。

`public/.nojekyll` 会在构建时拷进 `dist/`，脚本还会在发布副本里兜底再造一次。

## base 路径

`base` 不需要手写。`astro.config.mjs` 会从 `siteConfig.siteURL` 自动推导：

```js
const _siteURL = new URL(siteConfig.siteURL);
const BASE = _siteURL.pathname.replace(/\/$/, "") || "/";
```

`siteURL` 是 `https://11408-prog.github.io/azur_blog/`，所以 `BASE` 是 `/azur_blog`。

**只有一条要记住：`dist/` 的内容必须铺在 `gh-pages` 的根目录**，不能再包一层 `azur_blog/` 文件夹，否则访问线上地址会 404。

Astro 自己管的路径（`_astro` 产物、`<Image>` 优化图）会自动带 base，但**代码里手写的 `"/xxx"` 不会**，那是上线后最容易翻车的地方，见 [09](./09-路径与base.md)。

## 体积与推送

发布树约 360 MB / 1180 个文件（2026-11-02）：

| 内容 | 大小 | 推不推 |
| --- | --- | --- |
| `music/` 40 首 mp3 | 154.1 MB | ✅ 推（否则播放器没歌） |
| `_astro/`（字体、图片、JS、CSS） | 97.3 MB | ✅ 推 |
| `images/` 相册 | 45.0 MB | ✅ 推 |
| `assets/` 横幅等 | 24.7 MB | ✅ 推 |
| `posts/` | 17.7 MB | ✅ 推 |
| `img/` 文章图 | 5.9 MB | ✅ 推 |
| `assets/music/url/*.mp3` | 20.9 MB | ❌ **剔除** |

被剔除的是 Mizuki 模板自带的 4 首示例歌：`src/` 里没有任何地方引用，`dist/` 下的 html / js / css 里也搜不到 `assets/music`，纯属死重。脚本里对应 `$junkDirs`。

- 最大单文件约 10.5 MB（一首 mp3），远低于 GitHub 的 50 MB 警告线和 100 MB 硬限，**不需要 Git LFS**
- 某次推送超时，脚本会自动换大 `postBuffer` 重试一次
- 字体已经子集化，体积比 2026-11-02 当时小很多（见 [05](./05-字体与性能.md)），上面是当时的数字

## 推完之后怎么验证

### 看 Pages 构建

仓库 → **Actions** → `pages build and deployment`。legacy 模式下 GitHub 会为 `gh-pages` 的每次推送自动起这个 workflow，一般 1~2 分钟。

### 抽查线上

逐个确认：

- [ ] 首页 200，且源码里有 `/azur_blog/_astro/`（**不能**是裸 `/_astro/`）
- [ ] 文章页 200（随便抽 3 篇）
- [ ] 相册页 200，封面出得来
- [ ] 音乐播放器能播
- [ ] 搜索能用（部署脚本里 pagefind 那步成功才有索引）
- [ ] 浏览器标签页图标正常
- [ ] `Ctrl+Shift+R` 强刷后还是新的（排除缓存误判）

## 这次部署覆盖了旧站的哪些线上内容

force push 是整分支替换，旧 Hexo 站 `gh-pages` 上这些会从线上消失：

| 旧站内容 | 文件数 |
| --- | --- |
| `carousel/`（旧站画廊图） | 284 |
| `gallery` / `gallery.json` | 各 1 |
| `videos/`、`activity/`、`music/bgm.mp3` | 各 1~2 |

这些文件**没有真的丢**：它们在 `gh-pages` 的 git 历史里还能找回（脚本没有清历史，只是把分支头挪走）。取回方式：

```powershell
git -C <旧站目录> fetch origin gh-pages
git -C <旧站目录> checkout <旧的 gh-pages commit> -- carousel
```

推送前的最后一个旧站提交是 `0a084417`（2026-10-29），脚本每次运行也会打印远端当前的 `gh-pages` 头。

## CI 说明（需要你决定）

仓库里 `.github/workflows/deploy.yml` 会在**每次 push 到 `main` 时**构建站点并推送到 **`pages`** 分支，而你本地脚本发布的是 **`gh-pages`**，Pages 读取的也是 `gh-pages`。
也就是说：

- 这个 workflow 产出的 `pages` 分支目前没有被任何东西使用
- 它构建时拿不到本地的音乐和相册图，所以即使切过去也会得到不完整的站点

建议二选一：**删掉 `deploy.yml`**（保持纯本地部署），或者把它改成真正的发布流程再切换 Pages 的 source。`lint.yml` 现在监听 `main`，会在 push 和 PR 时运行代码检查。

## 常见失败与对策

| 现象 | 原因 | 对策 |
| --- | --- | --- |
| `schannel: SEC_E_NO_CREDENTIALS` | 系统 gitconfig 写死 schannel | 脚本已强制 openssl；手动 git 时带 `-c http.sslBackend=openssl` |
| `unable to get password from user` | credential helper 起不来 | 用 extraheader（脚本已实现） |
| `Cannot authenticate without a token` / `malformed token` | 没有 `.deploy-token` 或内容不对 | 重新生成 token，单独一行写进去 |
| `401 Bad credentials` / 403 | token 过期、权限不够或被撤销 | 重新生成 token |
| 线上白屏、资源 404 | 缺 `.nojekyll`，或 `dist/` 被包了一层 | 脚本会硬校验 |
| 页面还是旧的样子 | Pages 有 1~2 分钟延迟 + HTML 短缓存 | 等两分钟，再 `Ctrl+Shift+R` |
| 搜索框没结果 | pagefind 没跑成功 | 看脚本输出里的 `[WARN] pagefind`；需要 `pnpm install` |
| 音乐不能播 | `public/music/` 没同步 | `pnpm sync-music` 后重新部署 |
| 推送超时 | 体积大 | 脚本自动换大 buffer 重试；还不行就加 `-NoBuild` 重跑 |
| `reused cache entry` | 换了图但图片缓存没失效 | 别用 `-KeepCache`；清 `node_modules/.astro` |
